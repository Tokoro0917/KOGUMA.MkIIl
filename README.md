# KOGUMA MkIIl

STM32F446RE(STM32CubeIDE)をベースにしたマイクロマウス(迷路探索ロボット)のファームウェア。

## ハードウェア

- MCU: STM32F446RE(Cortex-M4, Flash 512KB, RAM 128KB)
- 開発環境: STM32CubeIDE 1.14.0

## ディレクトリ構成

```
Core/Src, Core/Inc   本体ファームウェア
Drivers/             STM32 HAL / CMSIS
KOGUMA.MkII/          旧バージョン一式(参考用に同梱)
test/                ホスト(PC)上で走る迷路アルゴリズムのテスト
.github/workflows/   CI設定
*.ioc                STM32CubeMX設定
STM32F446RETX_*.ld   リンカスクリプト
```

`Debug/`(ビルド成果物)とホストテストの実行ファイルは`.gitignore`で除外している。

## 迷路探索アルゴリズム(`Core/Src/Maze.c`)

2種類の最短経路計算を実装:

- **`Maze_Shortest_Calculation()`**: セル単位のBFS歩数マップに基づく最短経路。直交移動のみ。
- **`Maze_Dijkstra_Calculation()`**: 半セル(壁境界)単位のグラフ上でSPFA(キューベースのBellman-Ford)を用いたダイクストラ法。直進・斜め・コーナー継続でコストを変え(`ST_COST`/`DIAG_COST`/`CON_COST`)、斜め走行を積極的に使う経路を生成する。

どちらも生成した手順を`Shortest_Pass_Compression()` → `Shortest_Pass_Compression_NANAME()`で圧縮し、コーナーの大廻り・斜め入り/出のパターンに変換してから`Move.c`のモーター制御関数(`Short_NANAME_Move*`/`Short_Dijkstra_Move2000`など)が実行する。

ゴールは迷路中央の2×2区画(標準ルール)。どの面が開口になっているか大会では事前に分からないため、ゴール判定(BFS・ダイクストラとも)は2×2区画を囲む境界のどこから侵入しても「到達」とみなすようになっている。

### 行き止まり潰し(`Maze_DeadEnd_Fill()`)

確認済みの壁だけで出入口が1つ以下になったマスは、入った辺と同じ辺からしか出られないため、そのマス自身が始点/終点でない限り最短経路上に絶対に乗らない。エセ全面探索(ALL_MODE)は未探索マスを片端から目標にするので、放っておくとこうした袋小路のポケットにも寄り道してしまう。

`Maze_DeadEnd_Fill()`はそういうマスを`G_MAZE_Closed[][]`に記録し、**連鎖させる**。1マス閉じるとそのマスは隣にとって「出口」として数えられなくなるので、袋小路の通路が根元まで一気に潰れる。`Maze_Gool_Setting()`は閉鎖マスを全面探索の目標候補から外す。

呼び出しは`Maze_Wall_Update()`の4方向分岐、`Maze_Step_Calculate()`の直前。

安全側に倒すための作りが要点:

| 方針 | 理由 |
|---|---|
| `G_Maze_Row`/`G_Maze_Column`(実測の壁マップ)を書き換えない | マップの保存・表示・ダイクストラは今まで通り真の壁だけを見る |
| 閉鎖情報を歩数マップBFSの通行判定に使わない。使うのは目標選定だけ | 誤って閉じても起きるのは「そのマスを探索しない」だけ。経路が塞がる/帰還できなくなる経路が構造的に存在しない |
| 毎回ゼロから再計算(ステートレス) | 誤った閉鎖が累積しない。探索用⇔帰還用のゴール切り替えにも自動追従 |
| 未確認の壁は「開いている」とみなす | 既知の壁 ⊆ 真の壁 なので、探索途中の部分知識では完全知識より必ず閉鎖数が少なくなる |
| スタート・現在の目標・ゴール2×2区画は閉じない | スタートは初期状態で3枚壁。守らないと即座に潰れて帰還できなくなる |

`G_DeadEnd_Fill_Enable`を`0`にすると実行時に無効化でき、従来動作に戻る。閉鎖したマス数は`g_deadend_closed_count`で確認できる(`Maze_Mapping()`内にコメントアウト済みの可視化用printfあり)。

副次的な効果として、壁で完全に囲まれた到達不能マスは出入口0で必ず閉鎖されるため、ALL_MODEが通常の「未探索マス数が0」の経路でクリーンに終了するようになった(従来は「自分のマスがMAX_STEPのまま」を検出するフォールバック頼みだった。フォールバック自体は保険として残してある)。

### 迷路サイズ

`Core/Inc/Define.h`の`MAZE_SIZE`(既定16)を書き換えるだけで16×16⇔32×32を切り替えられる。壁ビット幅・ノード配列サイズ・キュー容量・ゴール座標は全てこの値から自動的に導出される。

32×32時のSRAM見積り(Maze.c分のみ、実測): 16×16で約11.6KB → 32×32で約43.6KB。現在`Short_Dijkstra_Move2000`はmain.cから未接続なのでリンカに削除されており、現状のビルドサイズには影響していない。32×32を実際に有効化する場合は、`Core/Src/LOG.c`の`LOG_MAX`(現在2000、既定3000から削減済み)を含めたRAM予算の再確認が必要。

## メイン動作モード(`Core/Src/main.c`)

ロータリーエンコーダの`Encorder_mode_out()`(モード)と`Encorder_number_out()`(ナンバー)の組み合わせで動作を選択する。

### モード0: 大会用(探索走行)

いずれも「往路: スタート→ゴール」「復路: ゴール→スタート」の2区間を走り、各区間の終わりで`Maze_Save()`する。

| No | 往路/復路の走り方 | 全面探索 | 復路後の最短走行 |
|---|---|---|---|
| 1 | スラローム探索 | **あり**(復路で実施) | なし |
| 2 | スラローム探索 | なし | なし |
| 3 | 吸引探索 | なし | なし |
| 4 | 吸引探索 | **あり**(復路で実施) | なし |
| 5 | 吸引探索 | なし | あり(直線5000mm/s, 加速15000) |
| 6 | 既知区間加速(`Robot_Maze_Pass_Action`) | なし | あり(直線6000mm/s, 加速15000) |
| 7 | 往路: 既知区間加速 / その後: ダイクストラ誘導の未知壁探索 | なし | なし |

No.7は往路でゴールに着いたあと、スタート→ゴールのダイクストラ経路上に残っている未確認の壁を、今いる位置から直接見に行く(`Maze_Unknown_Wall_Scan()`)。経路の再計算は毎回ではなく、ゴールに着いた直後とUターンしたときだけ行う。経路上の未知壁がなくなったらスタートへ帰る。

エセ全面探索(`Maze_Unkown_ALL_ModeSet()`)が有効なのは**No.1とNo.4だけ**。他は`Maze_Unkown_ALL_ModeSet()`の呼び出しがコメントアウトされている。したがって**行き止まり潰しが走行に影響するのもこの2つだけ**で、残りのモードの挙動は導入前と変わらない(`Maze_DeadEnd_Fill()`自体は常に計算されるが、結果を使う`Maze_Gool_Setting()`の分岐がALL_MODE時にしか通らないため)。

### モード1: 最短走行(速度・アルゴリズム違い)

`Short_NANAME_Move*(MAX, AC)`の`MAX`が直線区間の最高速度、`AC`が加速度。関数名の数字はコーナー通過速度。

| No | 経路生成 | コーナー | 直線最高速 | 加速度 |
|---|---|---|---|---|
| 1 | BFS | 2000 | 6000 | 15000 |
| 2 | BFS | 2000 | 6000 | 20000 |
| **3** | **ダイクストラ**(`Short_Dijkstra_Move2000`) | 2000 | 6000 | 20000 |
| 4 | BFS | 2000 | 6000 | 25000 |
| 5 | BFS | 2000 | 6000 | 30000 |
| 6 | BFS | 2400 | 6000 | 15000 |
| 7 | BFS | 2400 | 6000 | 20000 |
| 8 | BFS | 2400 | 6000 | 23000 |
| 9 | BFS | 2700 | 5000 | 20000 |
| **10** | BFS | **ターンごと**(`Short_NANAME_MoveTurnV`、下記) | 6000 | 20000 |

No.2とNo.3はパラメータが同一で、BFS経路とダイクストラ経路の比較用になっている。

### ターンごとの通過速度(`Short_NANAME_MoveTurnV`)

旋回で滑らない速度の上限は旋回半径で決まる(横加速度 v²/r ≤ 限界)ので、大回り180のように半径の大きいターンは速く、45入り・V90のような小さいターンは遅く回るのがよい。`Short_NANAME_Move2000`などは全ターンを同じ速度で回るが、この関数はターンの種類ごとに通過速度を持つ。

- 速度は`Move.c`の`TurnV_Table`の`v`で設定する。左右は同じ値を使う。**初期値は全部2000で、この状態では`Short_NANAME_Move2000`と同じ走りになる。**
- 旋回のパラメータは`Short_NANAME_Move2000`の値(2000で調整済み)を基準にして、通過速度Vに合わせて角速度を V/2000 倍、角加速度を (V/2000)² 倍にする。理想的には同じ軌跡(同じ旋回半径)で、横加速度が (V/2000)² 倍になる。前後のオフセット距離は理想的には変わらないが、実機では遅れで変わるので、速度を変えたターンは`offset_st`/`offset_end`を調整する。
- 直線の始点・終点速度は、前後のターンの速度に合わせる(`Core/Src/SpeedPlan.c`)。直線が短くて加減速しきれない場合は、その範囲までターンの速度を下げる(motor.cのcos加減速の距離の式を使い、直線の9割で加減速が収まるようにしている)。ターンが直線を挟まずにつながる場合は、遅い方の速度にそろえる。
- スタート区間の終わりとゴール停止区間の入口は、今までどおり2000が上限。

`Short_NANAME_Move2000`の値で見積もったピーク横加速度(速度2000、角速度が三角形になる場合の頭打ちを考慮):

| ターン | ピーク角速度[deg/s] | 横加速度[m/s²] |
|---|---|---|
| 大回り90 | 1514 | 53 |
| 大回り180 | 1220 | 43 |
| 斜め入り45 | 1854 | 65 |
| 斜め入り135 | 1500 | 52 |
| 斜め出45 | 1070 | 37 |
| 斜め出135 | 1350 | 47 |
| V90 | 2000 | 70 |

余裕がありそうなのは大回り180と斜め出45。ただしこの値は調整の結果でしかなく、本当の限界ではない。1つずつ速度を上げて、滑りとオフセットのずれを見る。

### ターンの調整

ターンのパラメータ(`TurnV_Table`)の調整には、別リポジトリのターンシミュレーター(`micromouse-turn-sim`)を使う。他の機体でも使うので、このリポジトリからは分けた。クラシック/ハーフ対応で、pidream「ターン調整のルーティン」の手順に沿った画面になっている。

シミュレーターの「前・後」は理想のターン開始点からの距離なので、`TurnV_Table`へ書き写すときは壁切れの分を換算する。

- 前(`offset_st`): `Motor_Wallcut_ST`は X/2 走ってから壁切れを待ち、残り X/2 を走るので `offset_st = 2 ×(前 − 壁切れ位置)`。`Motor_Wallcut_ST_NANAME`は壁切れを待ってから X を走るので `offset_st = 前 − 壁切れ位置`
- 壁切れ位置(シミュレーターの「曲がり始めの下限」に入れる値)は、今の表(Move2000の値)から逆算すると、通常の壁切れのターン(大回り90・斜め入り45・135)で約37mm、斜め出45 約25mm、斜め出135 約7mm、V90 約30mm
- `TurnV_Table`の角速度・角加速度は V_BASE=2000 での値なので、シミュレーターの値に (2000/v) と (2000/v)² を掛けて書く
- 後(`offset_end`)は、後ろの壁切れで早めに止まる分を実機で合わせる

## 壁センサの距離変換(`Core/Src/WallDistance.c`)

壁センサの値は距離に比例しない(近いほど急に大きくなる)。センサ値の差をそのまま制御に使うと、壁に近いときはゲインが効きすぎ、遠いときは効かなくなる。また左右のセンサで感度が違うため、`(L - 220) - (R - 200)`は単位の違う数どうしの引き算になる。`WallDist_mm(sensor, value)`はセンサ値を距離[mm]に変換する(表引き+直線補間)。

距離の定義: 横センサは機体の中心線から横壁の表面まで、前センサは機体の中心から前壁の表面まで。区画中心ではどちらも84mm。

**表は仮の値**。既存の定数(区画中心でL=220, R=200, 前=530)を基準に、センサ値が距離の2乗に反比例すると仮定して作っただけなので、実測値に置き換える必要がある。

### キャリブレーション手順(モード3 No.4)

1. モード3 No.4を選び、前センサに手をかざしてから横センサに手をかざしてスタートする
2. 約0.2秒ごとに`CAL,FL,L,R,FR,FL_mm,L_mm,R_mm,FR_mm`の形式でシリアル出力される(センサ値は100回平均、`_mm`は現在の表で変換した距離)
3. 横センサ: 機体を横にずらし、壁までの距離を44, 54, …, 124mmに合わせてL/Rの値を記録する
4. 前センサ: 前壁までの距離を34, 44, …, 174mmに合わせてFL/FRの値を記録する
5. `WallDistance.c`の表に書き写し、`test/test_walldist.c`を実行して表の並びが正しいか確認する
6. もう一度モード3 No.4で、`_mm`の列が実際の距離と一致するか確認する

手で機体を動かすとエンコーダのモード選択が変わるが、キャリブレーション中はループの中にいるので影響しない。終了はリセット。

### 横壁制御の距離化(`G_WallCtrl_Use_mm`)

`Wallsensor.c`の`G_WallCtrl_Use_mm`を1にすると、`calWallConrol()`の誤差を`(84 - 距離)`[mm]で計算する(壁の有無の判定は従来のセンサ値のまま)。既定は0で、従来の動作と変わらない。表を実測値に置き換えてから有効にすること。ゲイン`Kp_mm`/`Kd_mm`の初期値は、区画中心付近で従来の`Kp`/`Kd`と同じ効きになる値(仮の表での傾き約5.2[値/mm]を掛けたもの)。表を変えたら調整し直す。

## テストとCI

`Core/Src/Maze.c`はHALに依存しないので、ホストのgccにそのままリンクして迷路アルゴリズムを検証できる。

```sh
# 16×16
gcc -std=c11 -Wall -I Core/Inc -o test_deadend test/test_deadend.c Core/Src/Maze.c && ./test_deadend
# 32×32
gcc -std=c11 -Wall -DMAZE_SIZE=32 -I Core/Inc -o test_deadend32 test/test_deadend.c Core/Src/Maze.c && ./test_deadend32
```

`test/test_deadend.c`が行き止まり潰しについて検査する内容:

| # | 内容 |
|---|---|
| 1 | 完全迷路(全域木)200種。連鎖が根元まで効いているか、最短経路上のマスが1つも潰れていないか、スタートとゴール2×2区画が守られているか |
| 2 | ループあり迷路300種。閉鎖マスを通行不可としても最短距離が変わらないか |
| 3 | 壁を4割「未確認」に落とした探索途中の状態300種。部分知識でも同上 |
| 4 | 初期状態(外周のみ既知)で1マスも閉じないか(誤爆検出) |
| 5 | `G_DeadEnd_Fill_Enable`による有効/無効の切り替え |

1〜3では、素朴な「変化がなくなるまで全マス走査」で書いた**参照実装**と閉鎖集合が完全一致するかも突き合わせている。仕様そのものの正しさは最短距離不変の検査が、連鎖機構(ワークリストの積み忘れ・打ち切り)のバグは参照実装との一致が担保する役割分担。

テストは不変条件が壊れると非0で終了する。実際に`Maze_Cell_IsProtected()`の保護を外した改変版を通すと失敗を検出することを確認済み。

`test/test_walldist.c`は距離変換の表を検査する(センサ値が増えると距離が増えないこと、表の範囲が84mmを含むこと、補間の値)。

```sh
gcc -std=c11 -Wall -I Core/Inc -o test_walldist test/test_walldist.c Core/Src/WallDistance.c && ./test_walldist
```

`test/test_speedplan.c`はターンごとの通過速度の速度計画を検査する(全ターン2000のとき従来と同じ速度になること、連続ターンが遅い方にそろうこと、MAXやスタート・ゴールの上限を超えないこと、ランダムなパス2000本で全直線の加減速が距離内に収まること)。

```sh
gcc -std=c11 -Wall -I Core/Inc -o test_speedplan test/test_speedplan.c Core/Src/SpeedPlan.c -lm && ./test_speedplan
```

CIは`.github/workflows/maze-test.yml`で、masterへのpushとPRのときに16×16と32×32の両方と、距離変換の表の検査、速度計画の検査を実行する。ファームウェア本体のARMビルドは対象外。

- `Maze_Dijkstra_Calculation()`: FIFOキュー+早すぎる確定ロックによりダイクストラとして不正だった箇所をSPFA(再緩和可能なキュー)に修正
- 経路配列(`G_Short_Pass`/`_CP`/`_NANAME`)の終端が正しく0に戻されず、短い経路の後に前回の長い経路の残骸を読み進めてしまうバグを修正
- ダイクストラのゴール判定が「ゴールセルを通り抜けた奥の境界」を起点にしていたため、普通の最短(BFS)より1マス多く進んでしまうバグを修正。ゴール2×2区画を囲む8境界すべてを起点にするマルチソース方式に変更(侵入方向を問わず、区画に入った時点で停止)
- `LOG.c`の境界チェックの off-by-one(配列を1要素分オーバーランするバグ)を修正、あわせてログ長を3000→2000サンプルに削減してRAMを確保
